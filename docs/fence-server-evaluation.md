# Fence evaluation for tiny-agent on a Linux server

**Scope.** This evaluates Fence at commit `3d383314ed0b124fc3c5cf6e240dbc1a9d3c8ae4` from the supplied official clone, against `typescript/src/index.ts` and `typescript/src/cli.ts`. Fence's own claim is deliberately limited: defense in depth for *semi-trusted* commands, not a strong boundary against malicious escape, with no CPU, memory, disk, process-count, or fork-bomb controls (`docs/security-model.md`, **Limitations**; [Security model](https://fencesandbox.com/docs/reference/security-model)). That qualification must accompany any `--sandbox` claim.

## Executive conclusion

The current implementation has useful accidental-damage reduction, but it is not a truthful containment boundary for an agent:

* it fences only the `bash` tool; Node, model requests, and the `read`/`write`/`edit` implementations remain outside Fence;
* it grants every sandbox host `/tmp` read/write even though it creates a private `sandboxTmp`;
* its secret-name environment filter is heuristic and preserves many sensitive or behavior-changing variables;
* its three multi-token denies are not reliably descendant-enforced and may not even be the command Fence preflights, because Fence receives `/bin/sh -c …` as its top-level command;
* it silently inherits Fence feature degradation in restricted containers, most importantly loss of network-namespace isolation.

For a server, run **one externally configured Fence around the whole `tiny-ts` process**, per workspace invocation, rather than spawning Fence for every bash call. This is the only simple design that also constrains tiny-agent's direct filesystem tools and every descendant. It requires making the model HTTP client proxy-aware (Node native `fetch`/`http` does not honor proxy variables), allowing only the model endpoint, and using Linux `command.runtimeExecPolicy: "argv"` if multi-token command policy is claimed. Secrets may remain in the process environment for the client, but filesystem deny-read must protect credential stores and network egress must be narrow; Fence cannot prevent exfiltration to the allowed model domain.

If those changes are not made, retain bash-only wrapping but name it accurately (for example, “Fence-protected shell commands”), not “sandboxed agent.”

## What Linux Fence actually does

### Enforcement stack and prerequisites

Fence constructs a `bwrap` command with `--die-with-parent`, normally `--new-session`, `--unshare-pid`, and, only when detected as usable and no `allowedDomains: ["*"]` is present, `--unshare-net`. It adds optional seccomp, then mount policy, then runs a staged Fence bootstrap helper (`internal/sandbox/linux.go`, `WrapCommandLinuxWithOptions`; `docs/linux-bwrap-mount-sequence.md`, **Ordered Phases** and **Final Command Handoff**; `docs/linux-security-features.md`, **Security Layers**; [Architecture](https://fencesandbox.com/docs/reference/architecture)). `bwrap` and `socat` are required. Landlock needs Linux 5.13+; seccomp user notification for argv policy needs 5.0+; eBPF monitoring needs `bpftrace` and root/`CAP_BPF` (`docs/linux-security-features.md`, **Feature Detection**, **Fallback Behavior**, **Installing Dependencies**).

Landlock is applied inside the namespace by an embedded helper before the workload and stacks with bwrap mounts. If unavailable Fence falls back to bwrap; optional seccomp also degrades when unavailable. Explicit argv runtime policy instead fails closed when user notification is unavailable (`docs/linux-security-features.md`, **Landlock Integration**, **Argv-Aware Runtime Exec Policy**, **Fallback Behavior**).

Nested/container operation is conditional, not assured. A container commonly lacks `CAP_NET_ADMIN`; Fence then skips `--unshare-net` and direct host networking is no longer kernel-isolated, although proxy environment variables remain (`docs/troubleshooting.md`, **“bwrap: loopback…”**; `docs/linux-security-features.md`, **When network namespace is not available**). AppArmor/user-namespace policy can also prevent bwrap. Landlock itself can stack, but the troubleshooting page explicitly warns about nested sandbox constraints (`docs/troubleshooting.md`, **Nested Sandboxing Not Supported**). Provisioning must run `fence --linux-features` on the *actual server/container* and reject startup unless required features, especially network namespace, bwrap, socat, Landlock, seccomp filter, and (if used) seccomp user notification, are present. `--privileged` is an excessive workaround; grant only prerequisites after host review.

### Filesystem semantics

Normal mode is broad read-only host visibility (`--ro-bind / /`) with writable holes. `defaultDenyRead` changes this to explicit read-only binds for default system/toolchain locations plus `allowRead`/`allowExecute`; it is **not** a strict allowlist because defaults include `/etc`, `/proc`, `/sys`, `/run`, `/opt`, `/nix`, `/snap`, `/tmp`, and several real-user tooling trees. `strictDenyRead` suppresses those defaults (`internal/sandbox/linux.go`, `WrapCommandLinuxWithOptions`; `internal/sandbox/dangerous.go`, `GetDefaultReadablePaths`; `docs/concepts.md`, **Filesystem model**; [Configuration](https://fencesandbox.com/docs/reference/configuration)). `allowWrite` implies read and execute; writes otherwise default-deny. `denyRead` wins over readable grants, and `denyWrite` plus mandatory dangerous-path overlays win over writes (`internal/sandbox/path_check.go`, `CheckReadPath`/`CheckWritePath`; `docs/security-model.md`, **Filesystem**).

On Linux `/tmp` is always replaced with a fresh writable tmpfs, not the host `/tmp`; the bootstrap uses `/tmp/fence` and repairs unusable `TMPDIR`/`XDG_RUNTIME_DIR` (`internal/sandbox/linux.go`, `/tmp` mount block; `internal/sandbox/linux_bootstrap_env.go`, `applyLinuxBootstrapEnvironment`; `docs/linux-bwrap-mount-sequence.md`, **Special Mounts**). A host path below `/tmp` is visible only when explicitly exposed after the tmpfs (`internal/sandbox/linux.go`, `ExposedHostPaths` late mounts). Fence does not synthesize or change `HOME`; `~` and default user paths are expanded from the Fence process's host user (`internal/sandbox/utils.go`, `NormalizePath`; `internal/sandbox/dangerous.go`). Setting `HOME` only in the child environment therefore does **not** make Fence path normalization use that new home.

Plain configured paths are made absolute relative to Fence's cwd and `EvalSymlinks` is attempted when they exist; non-existent paths retain their lexical spelling. Globs are expanded at startup. Mount-deny logic canonicalizes targets where possible and avoids mounting over some symlink destinations (`internal/sandbox/utils.go`, `NormalizePath`; `internal/sandbox/linux.go`, `resolvePathForMount`; `docs/linux-bwrap-mount-sequence.md`, **Common Gotchas: Symlinked destinations**). This is startup-time resolution, not a general race-free promise: mutable symlinks and absent future paths need conservative parent grants/denies. Cross-mount repair exists because recursive root binds can miss private submounts (`docs/linux-bwrap-mount-sequence.md`, **Cross-Mount Repair**).

Fence protects shell startup files, `.gitconfig`, `.gitmodules`, `.git/hooks`, and `.git/config` as persistence targets (`internal/sandbox/dangerous.go`, `DangerousFiles`, `FindDangerousFiles`; `docs/concepts.md`, **Filesystem model**). A linked git worktree has a `.git` **file** pointing to metadata in the main repository. With only the worktree allowed writable, ordinary files work but git operations needing the external common/worktree git directories will fail unless those exact canonical metadata paths are also granted. Broadly granting the main repository defeats workspace separation; for concurrent untrusted agents, use separate clones or intentionally expose only the minimum worktree metadata, and keep hooks/config protected. Do not assume `denyWrite: [workspace/.git]` protects an out-of-tree common git directory.

### Environment, network, and concurrency

The Fence CLI preserves the inherited environment except stripping every `LD_*`/`DYLD_*` variable before launch (`internal/sandbox/sanitize.go`, `GetHardenedEnv`; `docs/security-model.md`, **Environment sanitization**). It does not generically scrub API keys or credentials. The Linux bootstrap sets upper/lower-case HTTP(S), ALL_PROXY and NO_PROXY variables and `FENCE_SANDBOX`; clients must cooperate (`internal/sandbox/linux_bootstrap_plan.go`, `buildLinuxBootstrapPlan`; `internal/sandbox/utils.go`, `GenerateProxyEnvVars`).

Default network behavior combines OS blocking of direct outbound traffic with localhost HTTP/SOCKS proxies that filter domains. A permitted domain is an unrestricted exfiltration channel; filtering does not inspect content. Node native `http`/`https` (and therefore ordinary native-fetch deployments) is specifically documented as non-proxy-aware; with a working net namespace it fails rather than being selectively allowed (`docs/security-model.md`, **How allowlisting works**, **Practical examples of proxy limitations**; [Security model](https://fencesandbox.com/docs/reference/security-model)). `allowedDomains: ["*"]` disables network unsharing and makes proxy-denies bypassable (`docs/configuration.md`, **Wildcard Domain Access**; [Configuration](https://fencesandbox.com/docs/reference/configuration)). Local outbound access is separate and requires explicit bridged host ports on Linux (`docs/concepts.md`, **Localhost controls**).

Each Manager starts HTTP and SOCKS listeners on `127.0.0.1:0`, so normal concurrent instances receive independent ephemeral ports; proxies are connection-concurrent, but a Manager is not thread-safe. One Manager per process/goroutine is required (`internal/proxy/http.go`, `HTTPProxy.Start`; `internal/proxy/socks.go`, `SOCKSProxy.Start`; `docs/library.md`, **Thread Safety**; [Go library](https://fencesandbox.com/docs/reference/library)). Fixed ports can collide. CLI `defer manager.Cleanup()` stops bridges and both proxies; `--die-with-parent` kills the namespace child if its Fence parent dies (`cmd/fence/main.go`, manager lifecycle; `internal/sandbox/manager.go`, `Cleanup`; `internal/sandbox/linux.go`, bwrap args). Abrupt `SIGKILL` cannot run deferred cleanup, though listener processes should die with their owning process; server supervision should still reap process groups and stale per-run directories.

Fence CLI signal handling forwards the first `SIGINT`/`SIGTERM`/`SIGHUP`, kills on the second, preserves signaled exit status as `128+signal`, and handles job-control details (`internal/sandbox/sigproxy.go`, `SignalForwarder`; `cmd/fence/main.go`, command start/wait and `resolveExitCode`). Tiny-agent's AbortSignal cancels its immediate `execFile` child, but this is not an explicit guarantee that every daemonized descendant is gone. Whole-process supervision should send TERM, wait briefly, then kill the process group/cgroup. Fence's PID namespace and `--die-with-parent` help; cgroups/systemd must supply resource and lifecycle limits Fence omits.

### Command policy, config trust, monitoring, API choice

Preflight parses the supplied shell string and checks prefixes. Default `runtimeExecPolicy: "path"` can enforce only single-executable denies in descendants; multi-token rules such as `git push` are preflight-only. Linux `"argv"` uses seccomp notifications to evaluate every descendant exec and fails closed if it cannot reconstruct it (`docs/configuration.md`, **Command Configuration**, **Enforcement Across Child Processes**; `internal/sandbox/command.go`, `CheckCommand`; [Configuration](https://fencesandbox.com/docs/reference/configuration)). Policies are not shell-proof authorization systems: allow rules override denies, shared/multicall and copied binaries have documented caveats, and filesystem/network controls remain the more dependable boundary.

The CLI discovers the nearest workspace/ancestor `fence.json[c]`, supports `extends`, and merges it with permissive OR/append behavior for many fields (`docs/configuration.md`, opening **Configuration**, **Merge behavior**). A repository-controlled config is therefore policy input from the code being constrained. A server must pass an absolute, administrator-owned `--settings` path outside every workspace, owned and writable only by the service administrator, avoid `@base` and repo-relative `extends`, and validate the resolved policy with `fence config show --settings …` ([Configuration](https://fencesandbox.com/docs/reference/configuration)). Tiny's generated private settings avoid auto-discovery, but their parent currently lives under host temp and their security still depends on service-user isolation and permissions.

`-m` reports blocked proxy traffic; Linux filesystem/syscall visibility additionally needs root/`CAP_BPF` and `bpftrace`, uses imperfect PID-range filtering, and seccomp denials may only appear to the program as `EPERM`. Monitoring is diagnostic, not enforcement (`docs/linux-security-features.md`, **Violation Monitoring** and eBPF fallback; `ARCHITECTURE.md`, **Violation Monitoring**; [Architecture](https://fencesandbox.com/docs/reference/architecture)). Centralize stderr/logs per invocation and never grant broad capabilities merely for nicer audit output.

The Go library exposes the same core wrapping but requires explicit helper dispatch/path on Linux, caller-supplied hardened env, caller cleanup and signal/stdio wiring, and lacks CLI platform monitors (`docs/library.md`, **CLI vs Library Differences**; [Go library](https://fencesandbox.com/docs/reference/library)). Because tiny-agent is TypeScript, shelling out once to the official CLI is substantially smaller and safer than creating a custom binding or long-lived manager service.

## Concrete problems in tiny-ts

1. **Boundary mismatch:** `runBash` alone invokes Fence (`typescript/src/index.ts:215-269`); direct file tools execute in the unfenced Node process. `typescript/src/cli.ts` advertises `sandbox: fence` for the whole session, which overstates coverage.
2. **Host temp overgrant:** it creates `sandboxTmp` and sets `TMPDIR` to it, but `allowWrite: [root, tmpdir()]` grants the host temp root (`index.ts:228-255`). Fence then replaces `/tmp` with an isolated tmpfs, so the created host `sandboxTmp` is not the effective in-sandbox directory anyway. The grant is unnecessary and misleading; on deployments where temp is elsewhere, it can expose cross-agent files.
3. **HOME mismatch:** Fence normalizes `~` using the service account's real home before the child gets `HOME=sandboxHome`. `CARGO_HOME` points inside the new home but is not included in `allowWrite`, while `/tmp` already supplies private ephemeral space.
4. **Read scope is wider than it looks:** `defaultDenyRead`, without `strictDenyRead`, includes Fence's large default system/tooling set. Adding every PATH directory, the Node installation parent, all of `RUSTUP_HOME`, and the workspace expands it further (`index.ts:223-243`). PATH entries must be canonicalized and administrator-controlled; a workspace-injected PATH directory becomes a read/execute grant.
5. **Secret filtering is not a security boundary:** matching variable names against `KEY|TOKEN|…` both over-removes innocuous values and misses sensitive names such as cookies, URLs with credentials, cloud-specific variables, SSH agent sockets, and arbitrary custom names (`index.ts:248-255`). Fence itself only adds loader-variable hardening.
6. **Command denies are incorrectly trusted:** `git commit`, `git push`, and `npm publish` are multi-token rules in default path mode. Fence's top-level preflight sees the explicitly passed `/bin/sh -c <command>` rather than necessarily parsing `<command>` as its own top-level string, and descendant path mode cannot enforce the multi-token intent (`index.ts:245-256`; Fence configuration section cited above). `denyWrite: root/.git` also makes ordinary commits impossible in a normal repository, while linked-worktree metadata lies elsewhere.
7. **Server install message is wrong:** Linux failure tells operators to use a Homebrew command (`index.ts:260-264`); official Linux prerequisites are `bwrap` and `socat` plus a Fence binary (`docs/linux-security-features.md`, **Installing Dependencies**).
8. **Cancellation/cleanup is best-effort:** a fresh Fence/proxy stack and temp directory are created for every bash tool call. This is expensive, increases lifecycle races, and concurrent calls create many ephemeral listeners. `finally` is good, but process-group/cgroup cleanup is not explicit.
9. **Feature degradation is unchecked:** `--sandbox` does not preflight `fence --linux-features`; inside a typical restricted container, commands may run without network namespace isolation while the UI still says “fence.”
10. **No resource containment:** the 120-second timeout and 10 MB capture cap do not bound CPU, RAM, disk, subprocess count, or background daemons. Fence explicitly omits these.

## Minimal server-appropriate design

1. **Deployment wrapper, one invocation:** an administrator-owned launcher creates/selects one canonical workspace, private session/state directory, and private temp directory, then executes:
   `fence --settings /etc/tiny-agent/fence-server.json -- tiny-ts <one-shot arguments>`.
   Use a separate OS uid where practical and one cgroup/systemd scope per run. Do not let the repo select config.
2. **Policy:** start with `strictDenyRead: true`; allow read/write only for the canonical workspace and a dedicated per-run state/temp tree; allow execute/read only for exact canonical runtime/toolchain paths. Keep the real service home, sibling workspaces, SSH/cloud credential stores, Docker/container sockets, and git common directories unreadable/unwritable. Do not grant host `/tmp`; Fence supplies an isolated `/tmp`.
3. **Network:** require successful net-namespace detection; deny by default and allow only the exact model API hostname(s). Replace native `fetch` with a proxy-aware client/dispatcher so whole-process Fence works. Never use `allowedDomains: ["*"]`. Recognize that prompts, workspace text, and environment data can be exfiltrated to the allowed model provider by design.
4. **Commands:** prefer filesystem/network enforcement over a long deny list. If retaining `git push`/publish/commit intent rules, set `runtimeExecPolicy: "argv"` and fail startup unless supported. Otherwise remove the misleading multi-token rules. Avoid exposing Docker/Podman sockets or privileged helpers.
5. **Credentials/environment:** construct an allowlisted environment (`PATH`, locale, model endpoint/key, minimal runtime values), rather than subtracting suspicious names. Keep the API key in environment only if required, and understand the agent process can send it/data to its allowed endpoint. Preserve Fence's `LD_*` stripping by using the CLI.
6. **Concurrency/worktrees:** independent Fence CLI processes and ephemeral proxy ports are safe by design. Give each agent a distinct canonical workspace and private state directories. Prefer separate clones when commits are required; otherwise keep linked-worktree external git metadata ungranted and document git as read-only. Never use fixed Fence proxy ports.
7. **Operations:** at startup verify the pinned Fence version and `--linux-features`; treat missing required features as fatal. Supervise the whole process group/cgroup with wall-clock, CPU, memory, PID and disk/quota limits; TERM then KILL on cancellation. Capture per-run Fence stderr. Use monitor mode only during policy tuning or where its capability cost is accepted.

This preserves tiny-agent's teaching-project simplicity: one external CLI dependency, one small static policy, one honest boundary statement, and host-native cgroup supervision—without pretending a per-tool wrapper is a complete agent sandbox.
