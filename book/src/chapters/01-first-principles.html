一句話掌握本章核心：LLM 是無狀態的文字預測函式，而 Agent 則是將其包裝在一個能夠「觀察環境（Observe） $\to$ 決定行動（Orient） $\to$ 執行工具（Act） $\to$ 接收反饋（Loop）」的閉環控制系統。本章只留下不可再簡化的第一性核心。

LLM 不是 Agent

在計算機模型中，單次 LLM 呼叫可以高度抽象為純函式：output = model(messages)。

模型既不會記住上一次的呼叫內容，也不具備讀檔、編譯程式或連線網路的系統權限。所謂的「延續上下文」，完全是外層 Host Application 在發起下一次 API 請求時，將先前的對話歷史重新打包送入的結果。

比較維度純大型語言模型 (LLM)智能代理 (Agent)
計算本質無狀態推論函式 f(context) -> output以狀態機為核心的閉環控制系統 (Control Loop)
狀態延續完全無狀態（單次 Request 結束即歸零）由 Host 透過 Append-only messages 陣列維持
環境副作用零（僅產生字串或 JSON 資料）有（透過 Tool Adapter 執行真實 I/O 與 Shell 命令）
終止條件產生 Stop Token 或達到長度上限模型判斷已獲得足夠資訊，產出最終解答 (Final Answer)

不可再刪的閉環 (Minimal Agent Loop)

以下是實現一個可用 Agent 所需的最小 TypeScript 實作。只要抽離這幾行中的任何一步，系統便無法運轉： 

async function runAgentLoop(userText: string): Promise<string> {
    // 1. 初始化對話歷史，寫入使用者目標
    messages.push({ role: "user", content: userText });

    for (;;) {
        // 2. 呼叫模型，注入當前累積的所有 messages 與可用 tools 定義
        const answer = await callModel(messages, toolDefinitions);
        messages.push(answer);

        // 3. 終止判斷：如果模型沒有要求呼叫 Tool，代表推論完畢，回傳最終文字
        if (!answer.tool_calls?.length) {
            return answer.content;
        }

        // 4. 副作用執行：循序執行模型要求的 Tool，並將結果以 role: "tool" 寫回
        for (const call of answer.tool_calls) {
            const result = await tools[call.name].execute(call.arguments);
            messages.push({
                role: "tool",
                tool_call_id: call.id,
                content: result,
            });
        }
        // 5. 回到迴圈頂端，攜帶包含 Tool Results 的最新 messages 再次呼叫模型
    }
}

這段程式碼完全不包含任何「修復 Bug」或「分析商業營收」的特定領域規則。它只專注於機械式的狀態排程：呼叫模型 → 派發能力 → 保存結果 → 決定是否迭代。

Coding Agent 的四個基本原子能力

只要為這個最小閉環配備以下四個核心 Tool，就構成了最小的 Coding Agent：

核心工具名稱本質功能系統對應操作安全性考量
read讀取檔案內容POSIX open() / read()路徑合法性、防止讀取二進位大檔撐爆 Token
write建立新檔或覆寫檔案POSIX O_TRUNC 寫入避免無預警破壞非目標檔案
edit針對指定字串區段精準置換精確字串比對與取代 (Exact Match)確認目標唯一性，防止誤改重名區塊
bash執行外部指令、編譯與測試execve() 子程序呼叫超時防護 (Timeout)、輸出字元截斷、非同步中斷處理

工程真實面：撰寫這個幾十行的 Loop 很容易，真正的挑戰在於生產環境的可靠性——當遇到網路錯誤、使用者中途中斷、Token 暴增、程式 Crash 崩潰時，系統如何保持 Transcript 合法且能安全復原？這正是後續章節要解決的核心問題。

第一性原則的責任邊界分配

在設計 Agent 架構時，模組權責劃分必須極度清晰：

系統層級 唯一職責 (Must Do) 嚴格禁止 (Must Not Do)
Model (大腦) 根據目前上下文判斷下一步，產出自然語言或 Tool Call 提議 直接取得系統憑證、直接操作 OS 硬體
Agent Runtime (心臟) 調度迴圈、管理 Message 狀態機、捕捉例外 在程式碼中寫死特定商業領域邏輯
Tool Adapter (手腳) 驗證參數、執行具體 I/O、捕獲錯誤並格式化回傳 超越 Host 授權邊界發動未定義的副作用
Session / WAL (記憶) Append-only 持久化記錄事件，支援 Crash 復原 在復原時盲目猜測未記錄的外部副作用狀態
CLI / Host (外殼) 提供使用者互動介面、配置安全環境與沙盒邊界 將部署安全責任推卸給模型自動判斷

動手驗證 (Hands-on Lab)

請在終端機中實際執行以下指令，觀察 Tool 邊界如何約束 Agent 的行為（需配置 OPENROUTER_API_KEY）： 

# 1. 賦予 read 權限：Agent 能夠讀取 README 並正常回答
tiny-ts --plugin read "讀取 README.md，說明 agent loop"

# 2. 僅賦予 edit 權限（缺少 read）：Agent 應明確拒絕並說明缺乏讀檔能力，絕不能胡亂捏造內容

核心收穫：Agent 的真實能力絕非 Prompt 中自我宣稱的文字，而是本次 Request 中 Host 實際注入並支援的 Tool Schemas。

在這個最小實作中，messages 陣列只暫存在 Process 的記憶體（Heap）中；一旦行程被殺死（Crash 或 kill -9），狀態便蕩然無存。在進入持久化儲存之前，下一章我們將先探討 Message 的規範化 (Normalization) 與 Provider Adapter，確保送入記憶體的每一筆資料都完全合法。
