一句話掌握本章核心：將 Agent 推向 Production 需要三道嚴密防線——測試金字塔證明架構設計在邊界內正確無誤；可觀測性（Observability）量化運行的真實成本與延遲；而安全邊界與執行膠囊（Execution Capsule）則確立系統永不越界的信任極限。

Agent 測試金字塔：三個層級的驗證

建立 Agent 測試體系時，切忌將所有測試都綁定在高昂且不穩定的真實 LLM API 上：

測試層級驗證核心目標是否消耗真實 API 額度？在 CI/CD 中的角色
1. Unit & ContractProvider 正規化、Pure Reducer 狀態重組、Pure Planner 決策❌ 否（純離線，毫秒級完成）Release Gate 核心門檻：任何 PR 必須 100% 通過
2. Conformance & IntegrationTS/Go/Python/Rust 四語言行為對齊、MCP 本機 Loopback 模擬❌ 否（使用 Mock Server）確保跨語言實作行為完全同構
3. Capability Eval驗證 Agent 能否自主修復真實 Bug 或重構程式碼✅ 是（呼叫真實 Model）定期評測與模型升級時的品質衡量標準

評估原則：Outcome 是客觀分數，Trace 是診斷解釋

在 Capability Eval 中，成績判定必須依賴客觀的外部驗證器（Hidden Verifier），而非由模型自我宣稱： 

1. 初始化隔離環境 ──→ 將評測程式碼複製至暫存目錄 (Temp Workspace)
                           ↓
2. 啟動 Tiny-Agent ──→ 執行修復任務 (記錄 Token, Latency, Tool 次數)
                           ↓
3. 執行隱藏測試    ──→ verifier.mjs 或 test.sh
                           ↓
4. 判定客觀結果    ──→ Exit Code 0 = PASS / 非 0 = FAIL
評分防弊準則：花費時間（Duration）、Token 消耗量與 Tool 呼叫次數僅作為「輔助效率指標」，絕不能用來補償錯誤的結果。一個少呼叫兩次 Tool 卻改錯 Bug 的 Agent，得分為 0。

結構化日誌（Structured Run Events）與 Prompt Cache 監控

生產環境中的 Agent 必須具備機器可讀的結構化輸出（如 tiny-ts --json "任務"），以便接入 OpenTelemetry 或 Prometheus 監控體系： 

{"type":"run.started","sessionId":"019...","model":"deepseek-v4-flash"}
{"type":"model.completed","durationMs":1250.4,"usage":{"input":150,"output":40,"cacheRead":1800,"cacheHitRate":92.3}}
{"type":"tool.started","toolCallId":"call_1","tool":"read"}
{"type":"tool.completed","toolCallId":"call_1","tool":"read","durationMs":8.2,"ok":true}
{"type":"run.completed","result":{"status":"succeeded","answer":"已成功修復檔案。"}}
監控維度關鍵指標 (Metrics)異常排查與警示
Prompt Cache 命中率cacheHitRate (%)若多輪對話中命中率突然從 90% 崩跌至 0%，代表 Prefix 出現動態變數（如未格式化的時間戳記）破壞了快取。
Tool 呼叫延遲durationMs監控外部 MCP 或 Bash 指令是否發生長尾延遲或卡死。
資料隱私保護Payload 脫敏Monitoring Events 預設不包含具體 Prompt 與 Tool 結果，避免在監控系統中複製客戶機密資料。

安全邊界矩陣：誰信任誰？

在計算機系統安全中，永遠不要信任未經驗證的輸入：

系統元件信任等級職責與安全邊界
Agent 核心程式碼🛡️ Trusted以最嚴謹的 TypeScript/Go/Python/Rust 核心控制狀態機轉移。
LLM 模型輸出⚠️ Untrusted產生的 JSON 參數視為外部不受信任輸入，必須通過 Schema 與 Runtime Guard 雙重校驗。
外部 Repository 程式碼⚠️ Untrusted專案中的依賴腳本或測試指令可能包含惡意程式碼，嚴禁在宿主機直接裸跑。
MCP 與 --plugin🔧 Tool Adapter僅作為能力選擇器，絕不能當作多租戶授權（ACL）或安全沙盒。

多租戶隔離：Execution Capsule（執行膠囊）

若你的產品需要為不同客戶運行 Agent 任務，單靠應用層路徑檢查絕對無法防禦攻擊。宿主系統必須提供 Execution Capsule：

  1. 資源配額限制（cgroups）：嚴格限制每個 Job 的 CPU、RAM、PID 數量與磁碟 Inode 上限。
  2. 網路出站防護（Egress & SSRF）：阻斷對雲端 Metadata 服務（如 169.254.169.254）與內網資料庫的非法存取。
  3. 生命週期終止階梯：中斷時依序發送 SIGTERM -> Grace Period -> SIGKILL，確保徹底清除 Process Tree。
