在討論 Agent loop 之前，先建立一套不含行銷術語的共同語言。本章從「模型實際收到什麼」開始，依序拆開 token、message、context、context window、tool call、session 與 memory。讀完後，你應該能沿著一次 request 的資料流，指出每一份狀態究竟存在模型、host process，還是外部儲存系統中。

先有一張正確的系統圖

大型語言模型（Large Language Model，LLM）可以先近似看成一個函式：輸入一串 token，輸出下一批 token 的機率分布。產品裡看似會聊天、會讀專案、會執行命令的「AI」，通常不是只有模型，而是 host application 把模型、資料與程式能力接在一起的結果。 

使用者
  ↓
host application
  ├─ 組合 instructions、對話、檢索資料與 tool definitions
  ├─ 呼叫 model
  ├─ 執行 model 請求的 tool
  └─ 保存 transcript / session
  ↓
model：根據本次輸入產生回覆或 tool call

這張圖最重要的邊界是：model 只看得到本次 request 中送進去的資料。它看不到你的檔案系統、資料庫、環境變數或上一次 API request，除非 host 明確把相關內容送入，或提供一個可取得它們的 tool。

抽象層次　本書會說「模型讀到訊息」或「模型選擇 tool」，這是方便理解的工程抽象。底層仍是數值張量、機率分布與 provider protocol；不需要先懂 Transformer 的矩陣推導，才能正確設計 Agent runtime。

推薦先看：建立 LLM 的直觀理解

在繼續閱讀 token、context 與生成流程前，推薦直接觀看下面這部影片。它能先建立模型如何接收輸入與產生輸出的整體直覺；觀看後再讀本章的工程定義，會更容易把模型本身與外層 Agent 系統分開。

Token：模型計算的基本單位

模型不是直接以「字」或「單字」為單位處理文字。Tokenizer 會把字串切成 token，再映射成整數 ID。常見片段、標點、空白與程式碼 都可能各自成為 token；同一段文字換模型或 tokenizer，切法也可能不同。 

原始文字  → tokenizer → token IDs → model → output token IDs → decoder → 輸出文字
  • 一個英文單字可能是一個 token，也可能被拆成多個。
  • 中文字不保證「一字一 token」；罕見字、組合字與不同模型都會改變結果。
  • JSON、縮排、重複 log、base64 與大型 tool result 都會消耗 token。
  • Token 數影響可容納的 context、延遲與費用，不能只用字元數估算。

工程上通常不必手寫 tokenizer，但必須知道 token budget 是有限資源。若 provider 宣稱 context window 為 128k tokens，意思不是可以放心塞入 128k tokens 的 prompt；還要替模型輸出、tool schema，以及 provider 可能需要的內部空間留下餘裕。

模型如何產生答案

模型每一步都根據目前 prefix，替下一個 token 計算條件機率 P(token | previous tokens)，再由 decoding policy 選出一個 token，重複直到停止條件成立。這解釋了三件事：

  1. 輸出不是資料庫查詢結果：模型產生的是在目前 context 下合理的序列，可能流暢但錯誤。
  2. 順序很重要：前面的 instructions、範例與 tool results 都會改變後續分布。
  3. 結果可能不完全固定：temperature、top-p、provider 實作與模型版本都可能造成差異。

Temperature 可以粗略理解成調整分布的尖銳程度：較低通常更集中，較高通常更多樣，但 temperature = 0 也不等於跨時間、跨硬體與跨 provider 的數學保證。需要穩定驗證的系統，應測試可觀察行為與資料 contract， 不能把「同一句話每次逐字相同」當成唯一 oracle。

Prompt、Message 與 Transcript

Provider API 通常不只接收一個字串，而是接收有角色與內容的 messages。不同 provider 的精確格式不同，但常見角色可先理解為：

角色用途典型來源
system / developer定義身分、規則、能力邊界與工作方式受信任的 host
user提出目標、問題與新資訊使用者或上游系統
assistant模型先前產生的文字或 tool callmodel response
tool某個 tool call 的執行結果host 的 tool adapter

Prompt 常被泛指「送給模型的輸入」，可能是一個字串，也可能包含完整 messages、tool definitions 與其他 request 欄位。Transcript 則是按順序累積的對話記錄。為避免歧義，本書在談資料結構時會盡量直接說 messages 或 transcript，不把所有東西都叫 prompt。 

[
  { "role": "system", "content": "你是 coding agent。" },
  { "role": "user", "content": "README 寫了什麼？" },
  { "role": "assistant", "tool_call": { "name": "read", "arguments": { "path": "README.md" } } },
  { "role": "tool", "tool_call_id": "call_1", "content": "# tiny-agent ..." },
  { "role": "assistant", "content": "README 介紹了……" }
]

角色不是裝飾。Host 必須保存合法順序與 tool call 的對應關係；不能把 tool result 偽裝成 user message，也不能只保留最後一段自然語言， 否則模型會失去「這份資料從何而來」的結構資訊。

Context 到底是什麼

Context 是模型在一次 generation 中可用的全部輸入資訊。在 Agent 系統裡，它通常不只包含聊天內容，還可能包含：

  • system / developer instructions；
  • 目前送入的 conversation messages；
  • tool definitions，包括名稱、描述與參數 schema；
  • 專案規則、檢索文件、程式碼片段與環境描述；
  • 先前歷史的 summary，或 provider 支援的其他輸入區塊。

Context 是本次推論的可見資料集合，不是永遠存在模型腦中的記憶。Host 即使在硬碟上保存了一百萬筆事件，只要本次沒有把它們 投影進 request，它們就不在模型的 active context 裡。

在 context 裡

  • 本次 request 實際送入的 instructions
  • 選入的歷史 messages 或 summary
  • 本次可用的 tool definitions
  • 剛寫回 transcript 的 tool result

不一定在 context 裡

  • 磁碟上存在但尚未 read 的檔案
  • 資料庫中未檢索的紀錄
  • 前一次 process 的記憶體
  • 被 compaction 移出 active context 的原始事件

Context Window 與 Token Budget

Context window 是模型單次推論能處理的 token 上限。可用一個簡化的不等式理解： 

instructions
+ conversation
+ tool definitions
+ retrieved data
+ 預留輸出
≤ context window

超過上限時，provider 可能拒絕 request、截斷輸入，或由應用程式先刪除內容。無論哪一種，都不能假設模型「會自己記得被截掉的部分」。 比上限更早出現的問題是注意力稀釋：資料雖然放得下，關鍵限制卻埋在大量無關 log 中，模型仍可能漏掉。

因此 context engineering 的核心不是「塞越多越好」，而是管理資訊的選擇、順序、來源與生命週期：

  • Selection：只選與目前決策相關的資料。
  • Structure：保留角色、來源、標題與邊界，避免無法辨識的文字堆。
  • Compression：摘要長歷史，但保留決策、證據、未完成工作與錯誤。
  • Retrieval：需要時才載入檔案、文件或技能正文。
  • Bounding：限制 tool result、schema、搜尋結果與輸出大小。
Prompt cache 不是更大的 context window　Cache 可以讓重複 prefix 的計費或延遲下降，但被 cache 的 token 通常仍占 context window。它解決重算成本，不解決 active context 無限成長。

Tool Call：模型提議，Host 執行

Tool calling 通常是 constrained structured output：host 把可用工具及參數 schema 送給 provider，模型回傳工具名稱與 arguments。 模型本身沒有因此獲得作業系統能力；真正的 effect 發生在 host 驗證並執行 call 之後。 

host 提供 read(path) schema
        ↓
model 產生 { name: "read", arguments: { path: "README.md" } }
        ↓
host 驗證名稱與 arguments
        ↓
host 讀檔，把結果作為 tool message 寫回
        ↓
model 在下一次 request 才看見內容

這個邊界帶來四條基本規則：

  1. Tool description 只告訴模型如何使用能力，不構成授權。
  2. 模型產生的 arguments 是不受信任輸入，必須做 runtime validation。
  3. Tool result 也可能包含不受信任內容，例如網頁中的 prompt injection。
  4. 是否允許讀檔、執行 shell 或連線網路，由 host 與執行環境決定，不由模型自行擴權。

Stateless、Session 與 Memory

「模型無狀態」是指一般 API 的下一次呼叫不會自動取得你上一次的 application state。某些 provider 提供 conversation ID、server-side response storage 或 prompt cache，但那是 provider / host 管理的狀態，不應誤認為模型權重在每次聊天後被更新。

名詞它是什麼通常存在何處
Model weights訓練後的參數；一般 inference 不會因你的對話立即改變model provider
Active context本次 generation 實際可見的輸入provider request / inference runtime
Transcript有順序的 user、assistant、tool messageshost 記憶體或 storage
Session讓一段工作可識別、保存、恢復的狀態與事件application storage
Memory產品術語；可能指摘要、偏好、向量檢索或持久 facts取決於具體設計
Knowledge in weights訓練時吸收的統計模式，不是可稽核資料庫model weights

所以「Agent 記得我的名字」至少可能有三種完全不同的實作：名字仍在 transcript；host 從使用者設定讀出後重新注入；或 memory service 檢索到一筆持久紀錄。只說「模型有記憶」不足以討論正確性、隱私、刪除或恢復行為。

RAG、Fine-tuning 與 Context 不是同一件事

三種常被混用的做法，改變系統的位置不同：

  • RAG / retrieval：先搜尋外部資料，再把選中的片段放進本次 context；資料可更新、可標來源，但檢索可能漏掉。
  • Fine-tuning：用資料調整模型參數，適合改變行為模式或格式傾向；不適合當精確、即時、可刪除的知識庫。
  • Prompt / context engineering：安排本次輸入中的規則、範例、資料與工具，使模型更容易完成當前任務。

讀取 repository 的 coding agent 多半使用 retrieval：先用搜尋或 read tool 找到相關原始碼，再把結果送回 context。程式碼沒有因而進入 model weights；下一個 session 若未再次載入，模型就看不到它。

建立正確直覺：六個常見誤解

  1. 「模型知道 repository 裡所有檔案。」 不知道；它只知道已送入的內容，以及可藉 tool 取得什麼。
  2. 「對話在 UI 裡，所以一定都在 context。」 UI 歷史可能只存在資料庫，active context 可能已摘要或裁切。
  3. 「Context window 放得下，就應該全部放入。」 成本、延遲、注意力稀釋與不受信任資料都會惡化。
  4. 「有 tool schema 就安全。」 Schema 不等於 runtime guard、authorization 或 sandbox。
  5. 「模型說已完成，就代表 effect 已發生。」 必須以 tool result、檔案、測試或外部系統狀態驗證。
  6. 「Session 保存了歷史，crash 後就能直接重做。」 外部 effect 是否已發生可能不確定；恢復需要明確的 durable protocol。

沿著一次 Request 追蹤資料

假設使用者要求：「讀取設定檔，找出 timeout，改成 30 秒並執行測試。」Host 可能依序進行：

  1. 把 system instructions、project rules、user message 與 read/edit/bash schemas 組成 request。
  2. 模型在 context 中看不到設定檔內容，因此產生 read tool call。
  3. Host 驗證 path、執行 read，將結果加入 transcript。
  4. Host 把更新後的 messages 再送給模型；這次 active context 才包含設定值。
  5. 模型產生 edit call；host 驗證並修改檔案，回傳結果。
  6. 模型產生 bash call；host 執行測試並回傳 stdout、stderr 與 exit status。
  7. 模型根據 tool results 產生 final answer；host 保存 session，UI 顯示結果。

注意：模型沒有在同一次 generation 中暗中讀檔。每個 tool call 都結束一次 model response；host 執行後，必須發出下一次 request，模型才看得到結果。 Agent loop 正是把這個往返自動化。

自我檢查

閱讀下一章前，試著不看答案回答：

  1. 檔案存在磁碟上，是否代表它在 model context 中？
  2. Provider prompt cache 命中，是否會釋放 context window？
  3. Tool call 的 arguments 應被視為可信程式輸入嗎？
  4. Transcript、active context 與 durable Session 有何不同？
  5. 模型回覆「測試通過」時，哪一份證據才能證明測試真的執行過？
答案　1. 否，除非內容被送入或經 tool 讀取後寫回。2. 通常不會。3. 不可信，必須驗證。4. Transcript 是訊息歷史，active context 是本次選入的可見子集，Session 是 host 保存與恢復工作的持久狀態。5. Bash tool 的可驗證結果，例如 command、exit status 與輸出，而不是自然語言宣稱。

現在可以精確描述 Agent 的材料了：model 負責根據 active context 選擇下一段輸出；host 保存 transcript、提供 tools 並產生 effect； Session 負責讓工作跨越 process 壽命。下一章把這些材料縮成一個不可再刪的 model → tool → result 閉環。
