一句話掌握本章核心：如果假設網路永遠正常、工具永遠成功、程序絕不崩潰，幾十行就能寫出 Agent；但生產環境的硬核挑戰在於崩潰之後的確定性。tiny-agent 採用資料庫級別的 WAL（Write-Ahead Logging）架構：先記意圖（Intent），再發動副作用（Effect）。

經典問題：被 kill -9 強制關閉後，指令到底執行了沒？

設想一個場景：Agent 剛決定執行 bash deploy.sh。就在系統發出指令的瞬間，作業系統觸發 OOM 或被 kill -9 強制終止。

若採用錯誤的「先做再記」策略崩潰重啟後的致命困境系統被迫面臨的代價
執行完畢才寫磁碟
execute() -> commit()		磁碟中完全沒有這筆記錄，系統處於「完全失憶」狀態。猜錯代價巨大：若重新執行會造成重複部署；若以為沒事則遺漏關鍵變更。
先寫意圖才發動副作用
commit(toolStarted) -> execute() -> commit(toolResult)		磁碟明確記錄「我打算執行 deploy.sh」，但缺少結束記錄。確定的未知：系統明確知道「此操作中斷」，可依法則安全標記 interrupted 且絕不盲目重放。

Durability 的精確承諾邊界

在計算機系統工程中，切忌使用行銷話術宣稱「永不丟失資料」。tiny-agent 嚴格定義其持久化邊界：

承諾維度是否保證技術原理與限制
Process-Crash Durability✅ 保證每一筆以 \n（LF）結尾的 JSONL 交易已交給 OS Page Cache。程式崩潰重啟時，自動丟棄末端殘缺的 Torn Tail，並從完整 Prefix 完美重建狀態。
Power-Loss Durability❌ 不保證未在每行寫入時執行極度耗損效能的 fsync() / fdatasync()。若整台伺服器瞬間斷電或硬體故障，未刷入快閃記憶體的 Cache 可能遺失。

單一 JSONL 檔案的兩類核心紀錄

Session 檔案由第一行的全域 Header 與後續的原子交易行（Transactions）組成： 

// Line 1: Header（不可變的全域設定與環境身分）
{"kind":"header","version":2,"id":"019...","createdAt":1787371200000,"cwd":"/workspace","provider":"openrouter","model":"deepseek/deepseek-v4-flash-0731","environmentIdentity":"/workspace"}

// Line 2+: 原子交易行（可以是一筆 Fact，或是多筆綁定的 Fact Array）
[
  {"kind":"entry","seq":1,"id":"019...","entry":{"type":"message","message":{"role":"user","content":"修復 Bug"}}},
  {"kind":"record","seq":2,"id":"019...","record":{"type":"runStarted","operationId":"...","operationKind":"run","inputEntryId":"..."}}
]

三種 Facts 職責劃分

tiny-agent 將存入 WAL 的事件嚴格分為三大類，避免將監控日誌與上下文混淆：

Fact 類型保存內容範例是否會投影給 LLM？主要用途
entryUser/Assistant 訊息、Tool 結果、Compaction 摘要✅ 會（依 Active Context 規則選入）維持模型推論所需的上下文與語意歷史
recordrunStarted, stepAttempt, toolStarted, abortRequested❌ 不會供 Reducer 與 Planner 進行狀態轉移與崩潰復原
usage每次物理 API 請求的 Token/Cache 消耗明細❌ 不會精確獨立的成本記帳本（Usage Ledger）

交易不變量 (Transaction Invariants)

  1. 單調遞增 seq：流水號從 1 開始，檔案內每一筆 Fact（包含 Array 內部）嚴格遞增 +1，絕不允許跳號或重複。
  2. 嚴格 UUIDv7 關聯：所有記錄皆使用時序唯一的 UUIDv7，父子參照必須指向已存在且歸屬合法的 Fact。
  3. 先持久化再更新記憶體（WAL 原則）：資料必須先以 LF 格式 Append 至磁碟，成功後才允許更新記憶體狀態機。
  4. Torn-Tail 容錯修復：最後一個 \n（LF）之後未完成的殘缺 Bytes 視為 Torn Tail，在 load() 時自動截斷修復；但如果某一行在 LF 之前就存在語法或欄位錯誤，則視為嚴重的 Corruption，系統選擇 Fail-closed 拒絕載入。

深而小的 Storage 介面

SessionStore 是標準的 Deep Module——以極簡的介面隱藏了極其複雜的交易流水號、ID 生成、隊列排程與尾端修復： 

interface SessionStore {
    commit(facts: NewFact[]): Promise<CommittedFact[]>; // 原子寫入多筆 Facts
    load(): Promise<SessionState>;                     // 載入、修復 Torn Tail 並重建狀態
    close(): Promise<void>;                            // 安全關閉檔案描述子
}

動手驗證 (Hands-on Lab)

親手製造一個帶有 Torn Tail 的損壞檔案，並觀察修復邏輯（不需消耗 API 額度）： 

# 1. 手工建立帶有殘缺尾部的 JSONL 檔案
tmp=$(mktemp)
printf '%s\n' '{"kind":"header","version":2}' > "$tmp"
printf '%s\n' '[{"kind":"record","seq":1}]' >> "$tmp"
printf '%s' '{"torn_tail_corrupted_json":' >> "$tmp"

# 2. 透過 Node.js 執行 lastIndexOf(10) 截斷修復
node -e '
  const b = require("fs").readFileSync(process.argv[1]);
  const lastLF = b.lastIndexOf(10);
  console.log("=== 修復後的純淨 Prefix ===");
  console.log(b.subarray(0, lastLF + 1).toString());
' "$tmp"
