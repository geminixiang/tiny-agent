一句話掌握本章核心：取消（Cancellation）不是單純「把 Promise 拋棄」，而是必須遵循嚴格的 先記 Abort 意圖再發送中斷信號 順序；歷史壓縮（Compaction）則是一次具備 雙切點（Two-Cut） 的正規交易，在縮減模型 Active Context 的同時，完整保留磁碟 WAL 供審計與復原。

中斷的正確順序：先持久化意圖，再發送信號

設想情境：工程師在 bash deploy.sh 執行時按下了 Esc。如果系統直接調用 abortController.abort() 卻未先寫入磁碟，一旦行程在此刻崩潰，重啟後系統完全不知道使用者曾要求中斷，可能會誤判為未知錯誤而發起重試。 

1. 持久化中斷意圖 ──→ commit(abortRequested) 落盤
                           ↓
2. 發送中斷信號   ──→ 向當前 Model API / Bash Child Process 傳遞 AbortSignal
                           ↓
3. 補齊結構化狀態 ──→ 將未完成的 Tool 標記為 interrupted，保持 Transcript 合法
                           ↓
4. 寫入終局記錄   ──→ commit(operationFinished: aborted)
                           ↓
5. 釋放系統資源   ──→ 關閉檔案描述子、終止背景 Process Tree

Cancellation 依 Phase 精準分流

當前運行階段 (Phase)具體中斷動作 (Signal Action)Durable WAL 狀態修復 (Reconciliation)
Model Phase中斷 HTTP 網路連線，終止串流接收將未結算的 Attempt 標記為 stepFailed(aborted)
Tool Phase向子程序發送 SIGTERM/SIGKILL 終止 Process Tree已啟動的 Tool 補寫 interrupted；未啟動的補寫 aborted
Compaction Phase中斷摘要生成請求關閉當前 Compaction Attempt，結束該 Operation

Abort Race 競爭條件的裁決鐵律

當「使用者按下中斷」與「模型/工具成功回傳」在同一毫秒發生時，系統必須將其嚴格序列化為兩種確定性歷史：

競爭勝出方判決條件最終歷史呈現
成功結算先落盤toolResult 或 assistantMessage 已成功寫入 WALAbort 操作判定該步驟已完成，不改寫已成功的結果，正常推進下一步。
abortRequested 先落盤中斷意圖已成功寫入 WAL遲到的成功回應一律作廢丟棄，該操作嚴格記錄為 aborted。

Compaction 歷史壓縮：雙切點（Two-Cut）架構

重要觀念：Compaction 絕非從磁碟中「刪除」舊資料！它是建立一個新的摘要節點（Checkpoint），在縮減 Active Context 的同時，將所有歷史原始事實完整保存在 Append-only WAL 中。

雙切點（Two-Cut）的嚴格定義

切點維度主要服務對象運作機制與邊界保證
Track 1: Active-Context CutLLM 大腦（推論視窗）保留最近至少 6 則訊息，並自動向前尋找 user 邊界（避免拆散單次完整問答）。前次產生的舊 Summary 會參與本次新摘要的計算。
Track 2: Durable Source Partition審計人員與 Crash Recovery嚴格記錄被壓縮的所有 compactedEntryIds、保留的 retainedEntryIds，並計算 sourceDigest 數位指紋，確保歷史不可篡改。
