一句話掌握本章核心：模型每次通話都是「失憶」的，連續性完全仰賴 Host 忠實重播 Transcript。但 Provider API 回傳的資料充滿了未規範的專屬雜訊，Host 必須建立一道 正規化防線（Normalization Seam），只保留標準 Canonical 欄位，徹底隔離不可信任的外部 Wire Format。

記憶體的本質：失憶的模型與忠實的錄音帶

想像模型是個每次通話都會瞬間失憶的專家。你每次撥電話給它，都必須把「我是誰、專案目標是什麼、我們剛才討論到哪、工具回傳了什麼結果」從頭到尾念一遍給它聽，它才能接著推論。

在系統架構中，這個「從頭到尾念一遍的錄音帶」就是 Transcript。

四種訊息角色的嚴格語意

Transcript 絕不是隨意的自然語言文字串，而是具有嚴格型別定義與角色約束（Role Invariants）的時序陣列：

Role (角色) 系統語意與職責 信任邊界 核心約束條件 (Invariants)
system 宣告 Agent 身分、行為準則、專案規則與 Skill 定義 受信任（Trusted Host 注入） 通常置於 Transcript 頂端，不可被使用者隨意竄改
user 使用者指令、外部事件或歷史壓縮摘要 (Summary) 不受信任（外部輸入） 不可偽造成 tool 或 system 語意
assistant 模型產出的推理文字或發起的 Tool Call 請求 待驗證（模型生成） 包含 tool_calls 時，後續必須有嚴格對應的 tool 訊息
tool 外部能力執行後的真實觀測結果 (Observation) 受保護（Host Tool Adapter 產出） tool_call_id 必須與前一則 assistant 中的 ID 精準吻合

合法 Transcript 是硬限制 (Strict Invariants)

主流 LLM Provider 對 Message 序列的合法性有極為嚴格的校驗機制： 

{"role":"assistant","content":null,"tool_calls":[
  {"id":"call_1","type":"function","function":{"name":"read","arguments":"{\"path\":\"README.md\"}"}}
]}
{"role":"tool","tool_call_id":"call_1","content":"# tiny-agent project..."}
常見錯誤序列 (Illegal Transcripts)引發後果tiny-agent 防禦機制
孤立的 Tool Call
發出 call_1 後行程崩潰，未寫入 tool 回傳即重啟		Provider API 直接回報 400 Bad Request，工作永久中斷崩潰復原時自動為未完成的 Call 補上固定的 Synthetic Interrupted Result
ID 不吻合
tool_call_id 與前項 assistant 的 ID 拼寫不同		模型推論上下文斷裂，拒絕繼續運算Runtime 強制驗證 ID 配對完整性
無故插入 Tool 訊息
在非 assistant 發起請求時自行注入 role: "tool"		破壞注意力分佈，違反 API 通訊協議嚴格由 Agent Loop 控制狀態流轉，不允許外部亂入

Provider Adapter 必須正規化（Normalization Seam）

核心踩坑警示：TypeScript 的 Type Assertion（如 response.message as Message）只存在於編譯時期，在 JavaScript Runtime 階段完全不會刪除任何欄位！

若直接將 OpenRouter / OpenAI 回傳的原始物件存入 Session，諸如 reasoning、refusal、annotations 等供應商專屬欄位會直接污染持久化日誌，導致 Strict Reducer 解析崩潰。 

// tiny-agent 的安全正規化實作：顯式白名單重建物件
function normalizeAssistantMessage(value: unknown): Message {
    const raw = value as Record<string, unknown>;
    
    // 1. 嚴格驗證角色
    if (raw.role !== "assistant") {
        throw new Error("Invalid role in assistant message");
    }

    // 2. 逐欄校驗 Tool Calls 結構完整性
    const toolCalls = Array.isArray(raw.tool_calls) 
        ? raw.tool_calls.map(validateToolCall) 
        : undefined;

    // 3. 僅挑選合法欄位建立全新 Canonical 物件（淘汰 reasoning / refusal 等雜訊）
    return {
        role: "assistant",
        content: typeof raw.content === "string" ? raw.content : null,
        ...(toolCalls?.length ? { tool_calls: toolCalls } : {}),
    };
}

Finish Reason 狀態映射

TL;DR：判斷是否執行 Tool，不能只看物件中有沒有 tool_calls 欄位，必須嚴格檢查 Provider 的 finish_reason。

Finish Reason模型生成狀態Host 正確處置
stop正常推理完畢，回傳 Final Answer結束 Agent Loop，將結果呈現給使用者
tool_calls / toolUse完整產生 Tool 調用名稱與參數進入派發流程，依序執行 Tool
lengthToken 上限觸發截斷
（Tool JSON 參數可能殘缺不全）		嚴格禁止執行該 Tool！寫入 truncated synthetic result，防止語法錯誤引發未知災難
content_filter / error觸發安全過濾或網路中斷保存失敗事件，不偽造 Assistant Completion

Token Usage 的精確計量

在多輪對話中，精確記錄每一次物理 Request 的 Token 消耗是成本控制與除錯的關鍵： 

type Usage = {
    input: number;      // 扣除快取後的純淨輸入 Token
    output: number;     // 本次生成的輸出 Token
    cacheRead: number;  // 命中 Provider Prompt Cache 的 Token 數
    cacheWrite: number; // 寫入 Provider Prompt Cache 的 Token 數
};

部分 Provider（如 OpenRouter）的 prompt_tokens 可能已將 Cache Tokens 混入計算，因此 tiny-agent 採用以下標準化公式： 

input = prompt_tokens - cacheRead - cacheWrite
cacheHitRate = cacheRead / (input + cacheRead + cacheWrite)
觀念辨析：單次 Request 命中率 vs. 累積總量　model.completed.cacheHitRate 代表「單次 API Request」的快取效益，能精準抓出哪一輪對話導致 Prompt Cache 破功；而整個 Run / Session 的命中率則必須透過累加器（Counters）重新計算，切勿將兩者混為一談。
