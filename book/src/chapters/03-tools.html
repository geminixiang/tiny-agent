LLM 只能提出 action；Tool 才真的讀檔、寫檔、查 Sentry 或呼叫 MCP。Tool 介面因此同時是能力 seam、測試表面與安全邊界。

小而深的 Tool 介面

export type Tool = {
    name: string;
    description: string;
    parameters: Record<string, unknown>;
    replay?: "safe" | "never";
    replayKey?: string;
    execute(args: ToolArgs, signal?: AbortSignal): Promise<string>;
};

Agent loop 不知道這是檔案、Sentry 還是 MCP。它只做四件事：把 schema 送給模型、依名稱找到 tool、執行、把結果寫回 transcript。這是 Strategy、Command 與 dependency injection 的最小組合，但 implementation 仍只是一般 object 與 array。

稍後你會再看到這個形狀：一個小而深的介面，把決策留給外面，自己只管一件事。

Schema 與 Execute 必須放在一起

一個 tool 的名稱、描述、參數 schema、runtime guard 與 implementation 應具有 locality。不要把 metadata 放一張表，再用 if (name === "read") 在另一處 dispatch。 

const readTool: Tool = Object.freeze({
    name: "read",
    replay: "safe",
    replayKey: "builtin:read:v1",
    description: "Read a UTF-8 text file...",
    parameters: {
        type: "object",
        properties: {
            path: { type: "string" },
            offset: { type: "integer", minimum: 1 },
        },
        required: ["path"],
    },
    execute: trustedReadExecute,
});

trustedReadExecute 是 tools.ts 中真實存在的函式：它負責分頁（offset/limit）與輸出上限（最多 2,000 行或 50 KB），但不做任何工作區路徑檢查。模型可以要求讀取任何這個 process 有權存取的路徑。

這是刻意的設計：tiny-agent 的 file tools 不做 application-level path containment。字串層級的路徑檢查與實際開檔之間存在 TOCTOU race，擋不住惡意並行的 filesystem mutation，卻會給人「已經安全」的錯覺；coding agent 也經常有正當理由讀取工作區之外的檔案（例如全域設定或依賴原始碼）。 因此檔案工具直接解析路徑並跟隨 symlink，真正的隔離交給外層 execution capsule 在 OS 層提供（見第 8 章）。

JSON Schema 不等於 Runtime Validation

Schema 是給模型的介面說明，不是安全檢查。模型或 provider 仍可能回傳：

{"command": 42}
null
[]

Dispatch seam 先要求 arguments 為 non-null JSON object；每個 built-in tool 再驗證自己真正執行的欄位。失敗必須 throw，由 Agent 轉成 error result。不要回傳一般字串 Error: ... 來表示失敗，否則 monitoring 只能猜文字。

Plugin 是具名 Tool Bundle

export type Plugin = {
    name: string;
    tools: readonly Tool[];
};

這不是 dynamic package system。--plugin read,edit 只是從 trusted built-in catalog 選擇本次提供的 capabilities。未指定時啟用四個 built-ins；指定後變成 allowlist。 

tiny-ts --plugin read "分析 README"
tiny-ts --plugin read,edit "閱讀並修改 README"

Repository 不能自行安裝 plugin，模型也不能要求下載任意 module。企業工具應由 trusted host 組裝，並透過 closure 持有 tenant scope 與 credential： 

function createSentryPlugin(client, trustedScope): Plugin {
    return {
        name: "sentry",
        tools: [createGetIssueTool(client, trustedScope)],
    };
}

Background Process：為什麼需要 bg

初學者很容易以為「要啟動 server，就讓模型呼叫 bash 跑 npm run dev」。問題是 bash tool 的語意是：執行一個命令，等它結束，再把 stdout/stderr 回傳。HTTP server、watch mode、dev server 則剛好相反：它們正常情況下不會結束。 

# 這對人類 terminal 很自然，對 agent tool loop 卻很麻煩
npm run dev

如果硬用 bash 做背景行程，agent 會開始學 shell 技巧：&、nohup、redirect log、 lsof 查 port、kill 停 process。這些不是 app 的重點，卻會佔掉很多 tool call，也很容易留下沒有關掉的 server。bg tool 就是把這件事變成一個小而明確的能力。 

{"action":"start","command":"node backend/server.mjs"}
{"action":"list"}
{"action":"list","status":"all"}
{"action":"status","id":"12345"}
{"action":"logs","id":"12345","tail":80}
{"action":"stop","id":"12345"}

bg start 會在目前工作目錄啟動一個背景 process，回傳的 id 就是 OS pid。它不假裝 server 已經健康，只表示 process 已經啟動且短暫觀察後還活著；真正的健康檢查仍應由 agent 用 curl 或測試命令驗證。 bg list 預設只列出仍在執行的 process；需要查看歷史紀錄時使用 status: "all"，也可以指定 running、exited、stopped 或 stale。

看得見的狀態：metadata 與 log

每個背景 process 都有兩個檔案，固定放在目前 cwd：

.tiny-agent/bg/<pid>.json
.tiny-agent/bg/<pid>.log

JSON 檔保存 command、cwd、pid、ownerPid、startedAt、log path 與 status。Log 檔保存 stdout/stderr，以及 process 結束時的 exit marker。這有兩個好處：第一，agent 不需要記住所有事情；第二，如果 tiny-agent 沒正常關掉，下次在同一個 cwd 啟動時，bg list 仍可以掃這些 metadata，知道哪些舊 process 可能還在跑。 

{
  "id": "12345",
  "command": "node backend/server.mjs",
  "cwd": "/tmp/demo-app",
  "pid": 12345,
  "ownerPid": 67890,
  "startedAt": "2026-08-29T09:00:00Z",
  "log": ".tiny-agent/bg/12345.log",
  "status": "running"
}

生命週期跟著 tiny-agent，但可被同 cwd 接手

正常情況下，tiny-agent 結束時會停止自己啟動的 bg process。這避免每次測試後都留下 server。可是現實中 process 可能 crash，或使用者可能強制關掉 tiny-agent；因此 bg 不只把狀態放在記憶體，也寫到 .tiny-agent/bg。同一個 cwd 的下一個 tiny-agent 可以 list、logs、status，必要時 stop。

這不是完整 supervisor：它不會 restart，不會做 health check，不會管理沒有 metadata 的外部 process，也不跨 cwd 掃描。它只補上 coding agent 最常遇到的缺口：啟動一個 server、看 log、打 API、停掉 server。

什麼時候用 bash，什麼時候用 bg

任務 適合的 tool 原因
跑一次測試、build、grep、curl bash 命令會結束，直接看輸出即可。
啟動 API server、frontend dev server、watch mode bg 命令會長時間存在，需要後續查狀態與停止。
檢查 server 是否真的可用 bash 跑 curl 或測試 bg 管 process，不代表 app health。

MCP 只是另一個 Tool Adapter

MCP tools/list → tiny-agent Tool[]
Tool.execute()  → MCP tools/call

MCP 不會建立第二個 agent loop，也不是 authorization 或 sandbox。Tiny-agent 只接受 trusted named catalog；URL、token、tenant 與 authorization 不能來自 model arguments。遠端名稱內部會編碼避免碰撞，TUI 才顯示成人類可讀的 mcp:sentry/get_issue。

目前 TypeScript、Go、Python 會把 MCP 能力適配進 generic Tool seam；Rust 仍使用獨立 McpTool dispatch。這是已知 cross-language difference，不應在教材中假裝完全一致。

Replay Policy 是 Effect Semantics

只有 exact built-in read 宣告 safe replay：

replay = safe
replayKey = builtin:read:v1

同名 custom read 仍是 never。bash/write/edit/MCP 預設 never，因為 crash 後無法證明 effect 沒有發生。Replay 不是由模型選擇，也不能只靠 tool name 判斷。

親手驗證

先跑 injected Tool 與 filesystem containment 的離線測試，不需要 OpenRouter key：

cd typescript
node --import tsx --test \
  --test-name-pattern="injected tool|paths outside cwd" tests/index.test.ts
cd ..

go -C go test ./cmd/tiny-go \
  -run 'TestFilesystemToolsOperateOutsideCwdIncludingSymlinks' -count=1

在 test 中追蹤四個步驟：model-facing schema、provider 產生的 call、runtime argument validation、tool result 回到 transcript。Symlink 案例證明 file tools 會跟隨 symlink 離開 cwd——這正是「檔案工具不是安全邊界」的具體證據；隔離必須由 OS 層 execution capsule 提供。完整安全邊界見第 8 章。
