一句話掌握本章核心：崩潰重啟後最危險的直覺，就是「把上次沒做完的指令再跑一次」。tiny-agent 將復原邏輯嚴格拆分為兩個 Pure Functions（純函式）：第一步只讀取 WAL 記錄還原狀態（Reducer）；第二步比對當前環境與設定決定決策（Planner）。

兩個完全隔離的 Pure Functions

在系統架構中，將狀態計算與外部 I/O 徹底分離是保證可預測性與可測試性的黃金法則： 

1. Reducer（純狀態重組）: reduceSession(wal_bytes) ──────────→ SessionState
2. Planner（純復原規劃）: planRecovery(state, currentConfig) ─→ RecoveryPlan
模組名稱輸入參數輸出結果設計鐵律
Pure ReducerJSONL 原始位元組串流SessionState 記憶體物件完全不接觸 I/O、不認識當前 Model 與環境，純粹依據歷史日誌進行數學狀態轉移。
Pure PlannerSessionState + 當前執行環境設定RecoveryPlan 結構化計畫不寫入磁碟、不發送 API、不分配 UUID，僅輸出下一步的行動決策。

四種復原結局：Retry、Replay、Blocked 與 Failed

工程師最常犯的錯誤是混淆 Retry 與 Replay，或混淆 Blocked 與 Failed：

復原結局精確定義與適用情境處理方式與責任方
Retry模型請求重試：前次推論時行程崩潰，且無外部副作用。Runtime 自動將相同 Context 再次發送給 Provider（嚴格限制最多 Attempt 2，防無界計費）。
Replay安全工具重放：前次執行 read 等無副作用工具時中斷。Runtime 自動重新執行該 Tool（僅限完全相符的 builtin:read:v1）。
Blocked安全阻斷：偵測到 Model 定義、工作目錄或環境金鑰已被竄改。立即停止自動運行，不寫入終局，交由人工介入排查（安全防護機制）。
Failed明確失敗：前次運行已收到 Provider 5xx 或明確 stepFailed 記錄。寫入 Failed 終局狀態，不再自動嘗試。

三道嚴格的安全校驗閘門 (Safety Gates)

在發動任何 Retry 或 Replay 之前，Planner 必須強制通過三道身分雜湊（Digest）檢查：

  1. Configuration Identity 閘門：
    比對 Model 名稱、System Prompt 雜湊、可用 Tool 清單與參數 Schema。若工程師在重啟前偷偷修改了 System Prompt，Planner 會判定為 configuration_changed 並拒絕重試。
  2. Environment Identity 閘門：
    比對工作目錄的真實物理路徑（Canonical Realpath）。若 Session 檔案被移動到其他目錄，Planner 會判定為 environment_changed 並阻止副作用發動。
  3. Replay Declaration 閘門：
    比對 Tool 的 replayKey。若自訂工具試圖覆寫內建工具名稱（如自製危險的 read 工具），系統會判定宣告不符並強制阻斷。
